# Surahs open in parts inside the app; a direct load gets the whole Surah

Opening a long Surah from the Surah index waited for its whole page: Al-Baqarah is about 6,100 Word cards, and on a throttled phone nothing changed on screen for seconds ([#24](https://github.com/addeelnayyer/quran-word-by-word/issues/24)). Now a Surah opened from inside the app (an index card, Continue reading, the Surah bar's Previous and Next links, the Language switch, Back and Forward) shows its header and a skeleton of its Ayahs at once and fills in its Ayahs as its Surah parts arrive. A Surah page loaded directly, reloaded or crawled is still the whole Surah in its HTML.

The two are told apart by the `rsc` request header. Every request the app's router makes, prefetches included, asks for a React Server Components payload with `rsc: 1`; a browser loading a page never sends it. Next documents the header as the one that "tells the server to return an RSC payload instead of HTML" and that a CDN must forward (`node_modules/next/dist/docs/01-app/02-guides/cdn-caching.md`, "Where CDN Caching Is Challenging" and "Handling Headers at the CDN", Next 16.3.6). A `beforeFiles` rewrite in `next.config.ts` with `has: [{ type: "header", key: "rsc", value: "1" }]` sends the router's requests for `/{lang}/{surah}` to `/{lang}/opening/{surah}`, a small static page with the Surah bar, the Surah header and the skeleton; the URL in the address bar stays `/{lang}/{surah}`. The Surah parts are static JSON files at `/parts/{lang}/{surah}/{n}.json`, one Language each, built from the dataset like every page. Because the opening page is small, the Surah links prefetch it again; the parts themselves are never prefetched.

A cache in front of the site keeps the two apart without anything of ours: Next already answers every App Router request with `Vary: rsc`, and adds an `_rsc` search parameter to the router's requests, so the opening page and the whole Surah page never share a cache key, even on a CDN that ignores `Vary`. The same document says Next means to move RSC requests to their own addresses (`/{path}.rsc`) in a later version; a rewrite keyed on `/{lang}/{surah}` would then stop matching, and the Surah opening scenarios (`features/site/surah-opening.feature`), which look for the skeleton, would fail on that upgrade.

On Back and Forward the opened Surah lands where that visit was left. A visit is the browser history entry, named by the Navigation API's `navigation.currentEntry.key`: Back and Forward return to the same entry and so the same key, while following a link makes a new entry with a new key. Nothing depends on how quickly the page comes back. A browser without the Navigation API opens the Surah as a link to it does, at the Reading place when that is in the Surah.

## Considered Options

- Streaming the one Surah page with Suspense: rejected because the pages are static, and a static page is prefetched and served whole, so nothing would show sooner.
- An intercepting route, `(.)[surah]` or `(..)[lang]/[surah]`: rejected because the first renders the old Language on a Language switch (the intercepted route keeps the Language it was opened from) and the second also intercepted `/{lang}/credits`, which then failed and fell back to a full page load.
- Loading every Surah in parts, direct loads included: rejected because a direct load, a search engine and a reader without JavaScript must still get every Word in the HTML.
- Prefetching the whole Surah: ruled out by the issue; it moves the same weight earlier instead of making less of it.
- Telling the router's requests apart by the `Next-Url` header: rejected. Next 16.3.6's router does send it on every request today (`client/components/router-reducer/fetch-server-response.js` and `segment-cache/cache.js` add it whenever the router state's `nextUrl` is set, and `create-initial-router-state.js` always sets it), but the documentation describes it as "added only for routes that use interception routes", so a later version may stop sending it for this site, which has none.
- Linking straight to `/{lang}/opening/{surah}` and showing `/{lang}/{surah}` in the address bar: rejected because Next's `Link` has no documented way to show one address and load another, and the opening address would be what is copied, shared and reloaded.
- Telling Back and Forward apart by how soon after a `popstate` the Surah opens: rejected because on a slow connection the page can take longer than any window, and it then opened at the Reading place instead of where it was left.
