# Allah references are two tables in the Account database's schema

Allah references live only in Neon ([0012](0012-allah-references-are-hand-marked-word-locations.md)), in the same database as reader data ([0011](0011-all-data-in-neon-behind-the-versioned-api.md)). Their tables are declared like the synced settings' and Reading places': as a Better Auth schema plugin (`apps/web/src/allah-references/schema.ts`), so `pnpm db:migrate` creates them with the Account tables, before each deploy and in each test run's own Postgres, and running it again changes nothing.

- **`allahReference`**: one row per Word location that is an Allah reference: `location` (`s:a:w`, unique) and `surah` (indexed), stored for reading a Surah's at once. One row serves both Scripts ([0002](0002-script-specific-quran-text.md)).
- **`allahReferenceRevision`**: one row per publish or seed: `surah`, `author` (the Admin's Account id, or `seed`), `createdAt`, the Word locations it `added` and `removed` (JSON arrays), the `base` version it was made against and the `version` it made, one more than its base. A Surah's version is its latest revision's `version`, and 0 before any revision; a publish whose base is not the current version is refused.

The seed, `pnpm db:seed-allah-references <file>`, writes both in one transaction: every Word location in the file, exactly as given, and one `seed` revision per Surah (base 0, version 1). It refuses the whole file, naming them, if any entry is not a Word of the Quran text (checked against each Ayah's Word count in the dataset, so Word 0 and an Ayah-end marker are refused too), and exits non-zero having written nothing. A Surah that already holds exactly the file's Word locations is left as it is, so a second run with the same file leaves every row as it was; a Surah that already holds other Allah references, from another file or a publish since, refuses the whole file too, so the seed never overwrites an Admin's work.

Pages read a Surah's Allah references through one server-side data module, `forSurah(surah)` (`apps/web/src/allah-references/for-surah.ts`), which answers its Word locations and version under the cache tag `allah-references:<surah>`, the tag a publish revalidates. The site does not use Cache Components, so the module caches with `unstable_cache`, the Next.js 16 guide's way to cache a database read without them. That cache outlives a build in `.next/cache`, so its key carries the build's time (`BUILD_TIME`, set in `next.config.ts`): each build reads Neon afresh, so a deploy after the seed shows what the seed wrote, while a publish refreshes a running build through the tag. The Surah page and each Surah part mark the Words it names, and a Word card draws an Allah reference's Arabic in `--allah`. When `DATABASE_URL` is unset, or the database does not answer within five seconds, a Surah has no Allah references: its pages still build and serve, with no gold, and the next revalidation fills it in.

A Surah part's JSON (`/parts/...`, [0005](0005-surahs-open-in-parts-inside-the-app.md)) marks such a Word with an optional `allahReference: true`, absent on every other Word. The parts are the website's own files, not the versioned API, so `/api/v1` and `/data/v1` keep their shapes ([0011](0011-all-data-in-neon-behind-the-versioned-api.md)); other clients will read a Surah's Allah references from an endpoint of their own (#150). Allah reference colour's light shade, #A87A0A, keeps 3.5 to 1 or more against the paper and the light Phrase colours, so an Allah reference's Arabic is held to WCAG's 3 to 1 for large text, which Quranic Arabic always is, where the rest of the Arabic keeps 4.5 to 1; the dark shade keeps more than 8 to 1.

## Considered Options

- A migration tool of our own (SQL files and a migrations table): rejected while Better Auth's schema already migrates the same database; two migration paths would each need running before every deploy.
- Keeping a Surah's Allah references as one JSON row per Surah: smaller, but a publish could no longer say which Word locations it changed, and the revision is where a Scholar reads that.
- Switching the site to Cache Components for `"use cache"` and `cacheTag`: the recommended path in Next.js 16, but it changes how every page renders, far beyond this one read.
