# Undoing an Allah reference publish is a revision that reverses it, made on the same lock as a publish; the revisions are listed to Admins only

An Admin sees a Surah's Allah reference revisions (#154) on an admin page of their own, `/admin/{surah}/allah-references`, reached from the Passage editor, and through an Admin-only `GET /api/v1/allah-references/{surah}/revisions`. It answers `{ surah, version, revisions }`, newest first (by version, highest first), each revision `{ version, base, createdAt, author, added, removed }`: `createdAt` an ISO 8601 time, `author` either `{ kind: "seed" }` or `{ kind: "admin", email, name }`, the Account the revision names ([0014](0014-allah-reference-tables.md)), and `added` and `removed` the Word locations, in Quran order. The page shows each Word as its Uthmani Arabic beside its Word location. A visitor is answered 401 and a signed-in non-Admin 403, as a publish is ([0043](0043-an-allah-reference-publish-is-a-post-of-the-changes-against-their-base.md)); the page sends them where every admin page does.

**Scholars are not let in yet.** The issue lets Scholars see the revisions too, but no Account holds a Scholar role in code: Admin is the only role, read from `ADMIN_ALLOW_LIST`. The owner chose Admins only for now; letting Scholars in waits for a Scholar role, a follow-up of its own. Until then nobody but an Admin sees the list.

**An undo** is `POST /api/v1/allah-references/{surah}/revisions/{version}/undo` with `{ base }`, the Surah's version the Admin saw. It reverses the publish at `version`: every Word location that publish added stops being an Allah reference, and every one it removed becomes one again, whatever revisions came between; a later publish's own changes are kept. It is written as a publish is: under the Surah's advisory lock, `pg_advisory_xact_lock(153, <surah>)`, refused 409 with `latest` when `base` is no longer the Surah's version, in one transaction that writes the changed Word locations and one new revision, `author` the Admin and `version` one more than `base`, naming the Admin as the content audit's actor ([0038](0038-content-audit-rows-name-an-actor-set-per-transaction-and-refuse-change.md)), then revalidating `allah-references:<surah>` so readers see it on their next load. It answers 200 `{ surah, version, locations }`. The revision records only what changed. Nothing is deleted: the undone revision stays in the list, and the undo is one more revision, so the history is never rewritten.

A revision by an Admin, a publish or an undo, can be undone; an undo of an undo puts the publish's changes back. **The seed's revision cannot be undone** (422): the issue asks to undo a publish, and undoing the seed would empty a Surah of the owner's list, which only a new seed should do. An undo that would change nothing, because later revisions already turned back every Word it would, is refused 422 rather than written as an empty revision. A path naming no Surah, or no revision of that Surah, answers 404; a body that is not `{ base }` 400.

## Considered Options

- Undo as going back to the Allah references as they stood before the publish: it would also throw away every later publish's changes to the same Surah, which the Admin did not ask to undo.
- Undo as deleting the revision and its changes: it would rewrite the history Scholars are to review.
- Undo through the publish endpoint, the editor sending the reversed taps: the server could not tell an undo from a publish, and the taps would be worked out from a list the Admin never saw.
- Letting the seed be undone: nothing asks for it, and it would empty a Surah's Allah references in one tap.
