# A Passage revision records the rows it changed, and an undo puts them back as a revision of its own, refused as a clash when a later revision changed them again

An Admin sees a Surah's Passage revisions (#174) on an admin page of their own, `/admin/{surah}/passages`, reached from the Passage editor, and through an Admin-only `GET /api/v1/passages/{surah}/revisions`, as the Allah reference revisions are listed ([0044](0044-undoing-an-allah-reference-publish-is-a-revision-that-reverses-it.md)). It answers `{ surah, version, revisions }`, newest first, each revision `{ version, base, createdAt, author, edits, undoes, changes }`: `author` either `{ kind: "seed" }` or `{ kind: "admin", email, name }`, `edits` the Passage and Phrase edits its Publish sent ([0047](0047-one-publish-writes-a-surahs-passages-phrases-and-allah-references-in-one-transaction.md)), `undoes` the version an undo turned back (null for a Publish), and `changes` the rows it changed. A visitor is answered 401 and a signed-in non-Admin 403. Scholars are not let in yet, for 0044's reason: there is no Scholar role.

**Each revision records the rows it changed.** `passage_revision` gains `changes jsonb`, `{ passages, phrases }`, each a list of `{ before, after }` in reading order: a Passage `{ from, till, en, ur }` keyed by its first Ayah, a Phrase `{ first, last }` keyed by its first Word, as their tables key them, and null on the side where the row did not exist. A Publish writes it in the transaction that writes the rows. The content migration `0014-record-passage-revision-changes` adds the column, and `undoes integer` with it, and fills `changes` in for the revisions made before it from the content audit ([0038](0038-content-audit-rows-name-an-actor-set-per-transaction-and-refuse-change.md)): a Publish's `passage` and `phrase` audit rows carry its transaction's `now()`, which is its revision's `created_at`, and its Surah. The seed's revision keeps `changes` null: the load made every row.

The edits alone could not be undone: an edit names a Passage by where it begins and a Phrase by its first Word on the rows it was made on, so replaying its inverse on rows a later Publish has changed means guessing. The rows it changed are exact.

**An undo** is `POST /api/v1/passages/{surah}/revisions/{version}/undo` with `{ base }`, the Surah's Passage version the Admin saw. It puts each row that revision changed back as it stood before. Rows the revision never touched keep whatever later revisions made of them. It is written as a Publish is: under the Surah's Passage lock, `pg_advisory_xact_lock(171, <surah>)`, refused 409 with `latest` when `base` is no longer the Surah's version, in one transaction naming the Admin as the content audit's actor that writes the rows, one new revision (no edit, `undoes` the version, its own `changes`, `version` one more than `base`) and the Surah's new content hash; then the Surah's Passage tag is revalidated and its page and parts warmed ([0046](0046-pages-read-each-surahs-passages-from-neon-under-its-own-cache-tag.md)). It answers 200 in the Publish's shape. It takes no Allah reference lock and writes no Allah reference: those have their own undo.

**A clash is refused 409** with the error naming the row and `latest`: when a row the undo would put back no longer stands as the revision left it, because a later revision changed it again, putting it back would undo that later change too, which the Admin did not ask for. So is an undo whose result would break a Passage or Phrase rule, such as a Phrase marked later across a boundary the undo would bring back. The Admin then undoes the later revision first, or edits by hand.

A revision by an Admin, a Publish or an undo, can be undone; an undo of an undo puts the revision's rows back. The seed's revision cannot be undone (422), for 0044's reason, nor one whose changes were not recorded (422), nor one that changed no row (422). A path naming no Surah or no revision of it answers 404, a body that is not `{ base }` 400.

## Considered Options

- Replaying the inverse of the revision's edits: an edit's inverse depends on rows later revisions may have moved, so it could split or join the wrong Passage.
- Recomputing a revision's changes, when listed, from the content audit: it ties the list and the undo to the audit's timestamps for ever; the migration reads them once.
- Putting back the whole Surah as it stood before the revision: it would throw away every later revision, as 0044 rejected.
- Undoing a clashing revision row by row, skipping the rows changed later: the result would be a mix nobody published, and could split a Passage from its title.
