# An Allah reference publish is a POST of the changes against their base, applied in one transaction

The Passage editor publishes an Admin's Allah reference changes (#153) through an Admin-only `POST /api/v1/allah-references/{surah}`, beside the public `GET` of the same address ([0028](0028-the-allah-references-endpoint-reads-neon-on-each-request-and-says-when-it-cannot.md)). The body is `{ base, changes }`: `base` is the version the changes were made on, and `changes` is the list [0035](0035-allah-reference-changes-are-a-list-of-their-own-kept-by-surah-and-version.md) keeps, the Word locations tapped, in order, each turning its Word into an Allah reference or out of one. The server replays the list on the Surah's Allah references at `base`, so two taps on one Word cancel out, exactly as the editor showed them.

A publish that passes writes, in one transaction, every Word location it added and removed and one Allah reference revision ([0014](0014-allah-reference-tables.md)): `author` the Admin's Account id, `createdAt`, the `added` and `removed` Word locations, `base`, and `version` one more than `base`. The transaction names the Admin's Account id as the content audit's actor ([0038](0038-content-audit-rows-name-an-actor-set-per-transaction-and-refuse-change.md)), as an Iltifat save does. It first takes a transaction-scoped advisory lock of that Surah's alone, `pg_advisory_xact_lock(153, <surah>)`, then reads the Surah's version: two publishes on one Surah queue, so of two made on one version one passes and the other is refused as stale, while publishes in other Surahs take other locks and never wait. The first key, 153, is this publish's own; another kind of data that locks per row picks a key of its own. Then it revalidates the Surah's tag, `allah-references:<surah>`, with `revalidateTag(tag, { expire: 0 })` as an Iltifat save does ([0023](0023-an-iltifat-save-writes-the-iltifat-and-its-revision-in-one-transaction.md), [0024](0024-surah-pages-and-parts-take-any-params-so-a-refreshed-tag-renders-them.md)), so the Surah page, its Surah parts and its Share pages are rendered again on their next request. It answers 200 with `{ surah, version, locations }`, the shape the `GET` answers, at the new version.

A refusal writes nothing and answers `{ error }`: 401 from no Account, 403 from an Account that is not an Admin, 404 for a path that names no Surah, 400 for a body that is not a publish, 422 when a change is not a Word of that Surah in the Quran text, and 409 when `base` is no longer the Surah's version, carrying the latest as `latest: { surah, version, locations }` so the editor shows it without a second request. Versions are kept per Surah, so a publish in one Surah never waits for or clashes with a publish in another. After a 200 the editor clears the list kept under the old version; after a 409 it shows the latest, and the list kept under the old version is set aside as 0035 says.

In the editor, Publish for Allah references is a button of its own in the Unpublished changes bar, "Publish Allah references", shown while Allah reference changes wait. The bar's Publish still sends only the Passage and Phrase edits, to git, so neither publish can half-land the other ([0012](0012-allah-references-are-hand-marked-word-locations.md)).

## Considered Options

- Sending the Surah's whole list of Allah references, as an Iltifat save sends the whole Iltifat: simpler to apply, but the revision would have to be worked out from a list the Admin never saw, and a Word tapped and untapped would look like a change.
- One Publish button for both kinds: the two writes go to git and to Neon, which share no transaction, so one could land and the other not.
