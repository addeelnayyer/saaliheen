# Next 16.3.6 is patched to expire cache tags on the clock that stamps them

An Iltifat save (#138, #142) revalidates its cache tags (`revalidateTag(tag, { expire: 0 })`, [0016](0016-iltifat-pages-render-on-request-cached-by-tag.md)), as each publish [0020](0020-pages-read-neon-on-request-warmed-after-each-deploy-and-publish.md) plans will, and the next read must show it. In next@16.3.6 the file-system cache stamps a tag's expiry with `Date.now()` (`dist/server/lib/incremental-cache/file-system-cache.js`, `revalidateTag`), and stamps each entry's `lastModified` with `Date.now()` too, but `areTagsExpired` (`dist/server/lib/incremental-cache/tags-manifest.external.js`) asks whether that expiry has passed by `performance.timeOrigin + performance.now()`, a second clock. The two drift apart as the server runs, about 1 ms a minute on a developer's Mac (#170's `s6r2-clock-drift.log`). Once `Date.now()` leads by more than the gap between a save and the next read, that read finds the expiry still "in the future" and is served the entry from before the save. #170's API run, long enough to reach that lead, read an Iltifat one save behind in 6 of 8 fresh builds; a 240 s idle before the Iltifat features alone did the same.

So the repo patches next@16.3.6 with `pnpm patch` (`patches/next@16.3.6.patch`, listed under `patchedDependencies` in `pnpm-workspace.yaml`): `areTagsExpired`, in both `dist/server/` and `dist/esm/server/`, reads `Date.now()`, the clock its stamps are made on. pnpm applies the patch at install, `pnpm install --frozen-lockfile` included, so CI, Vercel, `pnpm dev` and the standalone build the tests serve (whose `node_modules/next` is the patched copy the build traced) all run it.

## Consequences

- The patch is pinned to next@16.3.6: pnpm refuses to install a patch whose version no longer matches. Whoever upgrades Next must read the new `areTagsExpired` and `revalidateTag`: drop the patch if Next now compares on one clock, or re-make it with `pnpm patch` for the new version if it does not. Either way the API features' Iltifat saves, run after a few minutes of uptime, are the proof.
- On Vercel the patch ships but is not what keeps a save visible. `vercel build` runs in CI on the patched install, so each function's trace carries the patched file; but in Vercel's runtime the incremental cache is Vercel's own (the global `FetchCache`), not the file-system cache, so no `Date.now()` stamp is written there and tag expiry is Vercel's. Within one instance `areTagsExpired` now reads `Date.now()` where it read the monotonic clock; the only stamps it can meet are the "use cache" handler's below, and an instance's two clocks part by milliseconds, so a reader sees no difference. The bug this fixes is one of a long-running `next start`, standalone or `next dev` server: the tests' and a self-hosted one.
- The "use cache" handler (`dist/server/lib/cache-handlers/default.js`) stamps its own tags and entries with `performance.timeOrigin + performance.now()` and shares `areTagsExpired`; the site has no `"use cache"`. The file-system cache's `revalidateTag` runs after it and overwrites the tag's stamp with `Date.now()`, so with the patch that path compares on one clock too.

## Considered Options

- A cache handler of the site's own (`cacheHandler` in `next.config.ts`) that keeps its own tag manifest on one clock: the same fix with no patch, but a whole cache handler (memory, files, revalidation, the fetch cache) to own and keep in step with Next, for a one-line difference.
- Running the Iltifat features earlier, or polling in their steps: the tests pass, but a long-running server still serves an Admin the Iltifat from before the save, and the window grows with uptime (about 1.4 s a day).
- Stamping the expiry with the monotonic clock instead: `lastModified`, which the same check compares with, is stamped with `Date.now()` in several places, so the patch would grow and still mix clocks.
