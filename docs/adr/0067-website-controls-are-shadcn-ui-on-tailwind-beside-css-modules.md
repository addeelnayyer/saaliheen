# Website controls are shadcn/ui on Tailwind, beside the CSS Modules

Every control on the website (buttons, fields, tabs, switches, the dialogs and the Settings drawer) has been written by hand, each with its own markup, keyboard and focus handling and CSS Module, so each new one starts from nothing and they drift apart. [#297](https://github.com/addeelnayyer/quran-word-by-word/issues/297) makes them shadcn/ui components, in a sweep that changes nothing a reader sees; [#298](https://github.com/addeelnayyer/quran-word-by-word/issues/298) sets the stack up and proves it on the admin Surah picker.

A control on the website is a shadcn/ui component when one exists, styled through the mapped tokens; the reading surface (Quranic Words, Word meanings, the Scripts, and the Phrase, Allah reference, Known words and Iltifat colours) stays CSS Modules. That is the website only: the mobile app and the shared packages have neither Tailwind nor shadcn/ui.

- **Tailwind v4 beside the CSS Modules.** `apps/web/src/app/globals.css` begins with `@import "tailwindcss"`, compiled by `@tailwindcss/postcss` (`apps/web/postcss.config.mjs`). Tailwind's theme, base reset and utilities live in its cascade layers; the rest of `globals.css` and every CSS Module stay unlayered, and unlayered CSS wins over any layer whatever its specificity. So a page's own styles are never overridden by Tailwind, and a utility on a shadcn/ui part loses to a CSS Module rule on the same element: a control is styled through its utilities or through a Module, not both.
- **Radix underneath.** shadcn/ui's components are Radix primitives with Tailwind classes, vendored into `apps/web/src/components/ui/` by the shadcn CLI (`apps/web/components.json`; `cn` is `apps/web/src/lib/utils.ts`). They are our code once added: a vendored file is edited where the site differs, and says so at its top. Radix brings focus trapping and return, keyboard handling and announcements, which the hand-written controls each had to earn. The one `radix-ui` package is pinned to the version whose primitives the mobile app's Expo Router already resolves, so adding it moved nothing in the app's lockfile entries.
- **The tokens are the source.** No colour is added. `globals.css`'s `@theme inline` maps shadcn's names onto the site's tokens (background the paper, foreground the ink, primary the accent, secondary and muted the tint, accent the chip, border, input the line, ring the accent, destructive the madani brown, `font-sans` the UI typeface), straight onto Tailwind's `--color-*` rather than as shadcn's own `:root` variables, because the site already uses `--accent` and `--muted` for other things. As the tokens switch on `data-theme` and the system setting, so does every control, and Tailwind's `dark:` variant is redefined to the same rule (the reader's Dark choice, or the system's where the reader chose neither), so there is no separate dark theme. The corner radii are the site's: `rounded-md` is its 10px. Two site tokens have no shadcn name and are used as they are, `--scrim` under an AlertDialog and `--madani-bg` behind the Iltifat editor's Disputed tag (#300) and Delete Account's hover (#301): each is used in a place or two, so neither is mapped. So is a token the site's pages use that no vendored component reads (the Share page's gold, the Ayah highlight, the shadow colour), as `bg-(--gold)` ([#306](https://github.com/addeelnayyer/quran-word-by-word/issues/306)).
- **Focus and selection are the site's.** The vendored components drop upstream's focus ring and selection colours: the site's `:focus-visible` outline and `::selection` tint mark them, as they mark every other control. The outline's 6px corners are not forced on a shadcn/ui part (`[data-slot]:focus-visible` reverts them), so a radio item and a round button stay round when focused ([#300](https://github.com/addeelnayyer/quran-word-by-word/issues/300), [#306](https://github.com/addeelnayyer/quran-word-by-word/issues/306)). The Button's destructive variant draws its text in the paper rather than white (#301).
- **Preflight is loaded.** Tailwind's base reset comes with it, so a shadcn/ui part starts from the reset it is written against. Where the site had leaned on a browser default that Preflight takes away, the default is put back in the rule that needed it, with a `#298` comment: an editor icon's button padding (a stepper's, too, until its buttons became the vendored Button in #305), the Root page's headings and Spelling chevron (Preflight sizes pseudo-elements border-box), the Listen button's font, the Settings button's text colour, a tab count's `small` size, the Ayah numbers' `sup` (Preflight lifts it a second time), the bullets of the documents' and two admin lists, the margins of an Ayah translation paragraph and of the admin's notes, and the Known words and Roots list searches' placeholder grey. A link's underline is put back site-wide, in Tailwind's base layer so a utility can still remove it, for every link with an `href` that is not a shadcn/ui part (which carry `data-slot`).
- **The site's field and button are the vendored defaults.** The admin editors ([#300](https://github.com/addeelnayyer/quran-word-by-word/issues/300)) repeated the same overrides on every field, so the vendored Input, Textarea and NativeSelect carry the site's field (the surface fill, the line border, its padding, the text size of the form around it) and Button gains the site's plain button as its `secondary` variant (the tint with a line border, the chip on hover) and two sizes, `wide` (a form's full-width Save) and `compact` (a row's small button). A select stays the browser's own, as NativeSelect, so a keyboard and a phone open it as before; the reading pages' selects (the Surah bar's speed, the Share page's lists) keep the browser's arrow too, as `arrow="browser"` ([#306](https://github.com/addeelnayyer/quran-word-by-word/issues/306)). A Delete that was pressed twice (Delete, then Delete for good) opens an AlertDialog whose action is Delete for good. It is the same AlertDialog as Delete Account's, so the site's page hold holds the admin page beneath it too (#301).
- **The page-hold contract is the site's, not Radix's.** While a dialog or the Settings drawer is open the page beneath must not move: no wheel, trackpad, touch or key scrolling, no sideways shift, no scroll event, the Surah bar's form and the Reading place kept. [#301](https://github.com/addeelnayyer/quran-word-by-word/issues/301) settled it on the first dialog moved, the Delete Account confirmation. Radix's own scroll lock (`react-remove-scroll`) breaks the contract: it rewrites `<body>`'s padding to its margins, so the site's 16px page gutter goes and the page shifts sideways on a phone. Run beside the site's hold, it still rewrites the padding, so it is replaced. The lock lives only in Radix's `Overlay` (`DialogOverlay` wraps itself in `RemoveScroll`); the focus trap, the return of focus, hiding the rest of the page from assistive technology and Escape are all its `Content`'s. So a vendored dialog component keeps Radix's `Content` and puts a plain backdrop `div` of its own where Radix's `Overlay` was, and that backdrop calls `useHoldPage` (`apps/web/src/lib/hold-page.ts`): `overflow: hidden` on `<html>`, with padding taking over a scrollbar's room. One counter covers a dialog opened over another (the Root dialog over the Word grammar dialog). Radix's `Content` doesn't set `aria-modal`, so the vendored `Content` sets it, and the dialog is announced as modal, as a native modal `<dialog>` is. `apps/web/src/components/ui/alert-dialog.tsx` is the pattern; `Dialog` follows it (the Root dialog, the Particle dialog, the Word grammar dialog, the Surah bar's Surah picker and the Grammar page's, [#302](https://github.com/addeelnayyer/quran-word-by-word/issues/302), [#303](https://github.com/addeelnayyer/quran-word-by-word/issues/303), [#304](https://github.com/addeelnayyer/quran-word-by-word/issues/304), [#307](https://github.com/addeelnayyer/quran-word-by-word/issues/307)), and so does the Settings drawer's `Sheet` ([#305](https://github.com/addeelnayyer/quran-word-by-word/issues/305)). A step that looks for the page beneath by role waits for the dialog to close first, since Radix hides the page from the accessibility tree while the dialog is open.

## Controls kept custom

The sweep closed with [#307](https://github.com/addeelnayyer/quran-word-by-word/issues/307): the site has no native `<dialog>` left, nor the shared helper that opened one, nor a CSS Module rule that styled only a replaced control. A control the sweep leaves hand-written, because no shadcn/ui component behaves as readers expect of it, is listed here with its reason; a new hand-written control outside the reading surface joins this list or is a shadcn/ui component.

- **The destination links, the brand and the tab bar** (`site-bar.tsx`): links between the site's pages, the current one marked with `aria-current="page"`. shadcn/ui's Navigation Menu is a menu of disclosures, which readers would have to open; these are plain links.
- **The Language switches** (`language-link.tsx`, the Surah bar's): each Language is its own address, so each choice is a link to it, marked current. A Toggle Group would make them buttons that change the page in place, and the link (opened in a new tab, copied) would be lost.
- **An Ayah heading's Share and Listen buttons, and a Passage heading's Share** (`[surah]/ayah.tsx`): part of the reading surface, drawn by CSS on every Ayah of a Surah as long as Al-Baqarah. They are plain buttons with no behaviour of their own (one listener on the page reads their `data-` hooks), so a component per Ayah would only add weight.
- **A Word card's Root and Particle tags, and the Grammar page's Words** (`[surah]/word-card.tsx`, `grammar/[surah]/grammar-ayahs.tsx`): the reading surface again, in the Script's own type, on every Word; one listener opens the Root, Particle or Word grammar dialog from their `data-` hooks, as for the Ayah heading's buttons.
- **Quran Chat's citations** (`quran-chat.tsx`'s `.cite`): links to an Ayah set inside an answer's text, read as part of it, not as controls.
- **The Iltifat editor's Previous and Next ask the browser.** The links are shadcn/ui Buttons; their confirmation is not. With unsaved changes, leaving for a neighbouring Iltifat asks with the browser's own confirmation, as leaving the page by any other way (closing the tab, the address bar) must: one question, worded by the browser, for every way out. An AlertDialog would ask differently for these two links alone.
- **A Lemma's Spellings in the Root dialog are a plain list.** The Lemma row is a Collapsible and its Trigger; the Spellings beneath are the list the row's `aria-controls` names, there and hidden while collapsed, rather than Radix's CollapsibleContent, which wraps them in a div and leaves the page while collapsed, so the row would name no panel (#302).
- **The Word cards of the Marked Words and Supplication span editors, and of the admin Surah editor's Phrases, are reading surface.** Each is a button (`iltifat/[id]/word-marking.tsx`, `supplications/[id]/span-marking.tsx`, `[surah]/phrase-ayah.tsx`), but it shows a Quranic Word in the reader's Script with its Iltifat, span or Phrase tint: it stays a CSS Module, as the Words it mirrors do.
- **The Surah bar's Surah names and the Settings button keep their bar's look.** Each is a Radix Trigger (the Surah picker's `DialogTrigger`, the Settings drawer's `SheetTrigger`), so its behaviour is shadcn/ui's; what it draws is the bar's own: the Surah's number and its names in the Quran's type, and the gear beside the site bar's destinations, from the bar's CSS Module. A Button would bring a look only to have the Module override it.

## Consequences

- A control's look is in its utilities, mapped onto the tokens: a changed token changes every control, and a CSS Module rule on a shadcn/ui part silently wins over its utilities.
- An element that relied on a browser default and is added later has to set it itself; Preflight's reset is the starting point everywhere, including the reading surface.
- A control can match its old look only by overriding the vendored defaults (sizes, padding, the ghost hover, the hover transition), as the admin Surah picker does; its placeholder now takes the muted token instead of the browser's grey. If the sweep repeats the same overrides, they belong in a variant of the vendored component, or in its defaults when every use repeats them: the Input's box is the site's field look, which the Surah picker's search and the Account test sign-in both overrode it to (#301). The admin Surah editor ([#299](https://github.com/addeelnayyer/quran-word-by-word/issues/299)) put them there: the vendored Button shows a pointer, changes without a transition and answers a tap at once; its outline and secondary variants are the site's bordered surface and bordered tint; its `control` size is the site's 14px button. The vendored Toggle has a `pill` variant and size, the editor's rounded choices. On the reading pages ([#306](https://github.com/addeelnayyer/quran-word-by-word/issues/306)), the tinted pill the site's bars and pages offer (the Surah bar's Listen and Share Ayahs, a Retry, a Spelling's Show more) is Button's `pill` variant and size, and the accent pill that never dims on hover (Sign in, Ask, Play) its `filled` variant. A look only one control has stays in its own utilities.
- A switch whose name is written on it and has no knob (the editor's Phrases and Allah references pills) is a Toggle given `role="switch"` and `aria-checked`, not shadcn/ui's Switch, which is a thumb on a track beside its label.
- tailwind-merge drops a vendored class only when an override has the same variant: a group or data-attribute variant upstream sets (a horizontal Tabs list's height, an active tab's shadow, a link Badge's hover) is overridden under that same variant.
- The Settings drawer's on/off settings (Hide Word meanings, Phrase colours, Allah reference colour, Known words colour, Ayah translation) and the Supplications switches are the same vendored Switch as Memorized?, named by the label written on it (#305).
- Radix's single ToggleGroup is a radiogroup of radios; the site's segmented switches (the Script, the theme, Section marks, the Ayah layout) have always been a group of toggle buttons, the chosen one pressed. The vendored ToggleGroup keeps that role, so a single group says it is a group and each item a button with `aria-pressed` (#305).
- A reader setting is right at first paint, before hydration, because `<html>` carries it; a prerendered page (Me) renders its controls without knowing it. So a reader setting's chosen option and its switch's on look are drawn from `<html>`'s attribute (`site-bar.module.css`), not from Radix's `data-state`: the Switch's track colour and thumb place are CSS variables a stylesheet can set (#305).
- Radix's modal Content closes on a press outside, before the click, which then lands on the page beneath once the backdrop is gone; the vendored Sheet ignores the press and its backdrop closes on the click (#305).
- `shadcn add` can write its `cn` import as an npm package named `cn` and add it to `package.json`; what it adds is checked before it is kept.
- A `Dialog` opened from a control that isn't its Radix `Trigger` gives focus back in `onCloseAutoFocus`: focus given back before then is pulled back in by Radix's focus trap (#303).
- Memorized? has a knob, a thumb on a track, so unlike the editor's pills it is shadcn/ui's Switch; its label is written on it, as on every switch the site draws, so the vendored Switch is the tinted pill holding the knob and the label, and is named by them (#302).
- Radix's AlertDialog never closes on a click outside, and every dialog on the site does, so the vendored `AlertDialog` keeps its open state itself, controlled or not, and its backdrop closes it on a click; no caller wires anything (#301). The vendored `Dialog` does the same (#303), though Radix's Dialog closes on a press outside by itself: it closes on the press, so the backdrop is gone before the click, which lands on the page beneath (on a Grammar page's Word, opening another dialog). Its closing on a press outside is turned off.
- The Makki/Madani filter of the Surah index and the Surah bar's picker is a ToggleGroup like the reader settings' segmented switches, its chosen option drawn by Radix's `data-state`, since it is the page's state, not a reader setting on `<html>` (#307).
- Radix's `Tabs` show only the selected panel, and its roving focus makes no tab a tab stop until one has been focused. The Surah index's two lists lie side by side on a track a swipe moves (#193), so both its panels are force-mounted, and each tab is given its tab stop by whether it is selected, as the tabs pattern has it (#304).
- Presentational components (Button, Input, Textarea, NativeSelect, Badge) carry no `"use client"`, so Server Components can use them; only those with Radix behaviour are client components.

## Considered Options

- **Tailwind in a layer under the CSS Modules without Preflight**: no fallout to fix, but shadcn/ui's parts are written against the reset and would each need theirs put back by hand.
- **Moving the CSS Modules into a layer above Tailwind**: the same precedence, but every Module would have to be wrapped, and an unlayered rule anywhere would still beat them.
- **shadcn's own `:root` variables in `oklch`, switched by a `.dark` class**: a second set of colours to keep in step with the tokens, and a second dark switch beside `data-theme`.
- **Radix's scroll lock alone, or beside the site's page hold** (#301): both take the page's gutter away (the confirmation's phone scenario moved the page 16px sideways).
- **Dropping Radix's lock with `modal={false}`**: that drops the focus trap and the page's hiding with it.
- **A shared UI package for the website and the app**: the app is React Native, which shadcn/ui and Tailwind's CSS do not serve.
